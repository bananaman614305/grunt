# ADR-017: Personal-fact memory

Status: accepted, 2026-09-18. Extends ADR-011 (preference memory) and crosses,
for this one store only, the no-content line ADR-003 drew and ADR-011 kept.

## Context

ADR-011 gave Milo a memory of *how* a caller wants answers made, and made a
point of storing nothing the caller said: every preference row is a
closed-vocabulary label, so the table can never leak a sentence. That was the
right bar for preferences, whose whole content is one of seven labels.

It is the wrong bar for the other durable thing an agent re-teaches every
session: **facts**. "My deploy account is `acct_4Q…`", "the staging box is
`10.2.0.7`", "my co-founder is Dana, she owns billing", "we spell it
`gray`, never `grey`". None of these is a label from a fixed vocabulary; the
value *is* the content. A memory that cannot store the content cannot store a
fact. So a fact store has to keep the user's words — the exact thing ADR-003
and ADR-011 refuse to keep.

We keep them, and we pay for keeping them with three guarantees that the
preference table never needed because it held nothing worth protecting.

## Decision

### The line this crosses, and only here

Milo stores personal-fact content — the user's own words — encrypted at rest,
in one table, `facts`. This is the sole place raw request content is
persisted. Everything else stands: the decision log stays content-free
(ADR-003), preference rows stay closed-vocabulary labels (ADR-011), user
OpenRouter keys are still never stored, and no fact content ever reaches a
log line, a header, a decision row, or an error message. The crossing is
scoped to this store and bought with the three non-negotiables below.

### Three non-negotiables, because it is PII

1. **Encrypted at rest.** `facts.content_encrypted` holds the fact text
   through the existing AES-256-GCM envelope (`packages/billing/src/crypto.ts`,
   keyed by `MILO_ENCRYPTION_KEY`) — the same envelope, the same key, the same
   path that already protects the account's OpenRouter sub-key. The plaintext
   exists in the row only as ciphertext; it is decrypted only to serve the
   owner or to judge relevance, never written back anywhere.
2. **Fully listable.** `GET /v1/memory` returns every fact the calling key
   stored, decrypted, with its category and provenance. Nothing is hidden;
   a stored fact the user cannot see would be a stored fact the user cannot
   trust.
3. **One-call deletable.** `DELETE /v1/memory/:id` removes one fact.
   Rotating the key orphans the whole set (the rows are keyed by the key
   hash, ADR-008), but a user should not have to rotate a key to be
   forgotten.

### Default-on, with a per-key kill switch

Fact memory is a Milo feature, not an opt-in: a key that never touched a
setting has it on. The kill switch is a per-key row in `fact_settings`
(`enabled`, default 1); `PUT /v1/memory/settings { "enabled": false }` turns
capture and injection off for everything from that key. A request can also
skip injection for one call with `milo: { "facts": false }`, symmetric with
ADR-011's `brief`.

If the deployment has no encryption key — billing (and thus
`MILO_ENCRYPTION_KEY`) is not configured — the feature **degrades to
disabled**: nothing is captured, nothing is injected, `GET /v1/memory`
answers empty and says so. A fact store with no envelope to encrypt with must
not store plaintext, so it stores nothing.

### Keys and scope

One row per fact, keyed by the SHA-256 of the caller's bearer credential (the
account key's hash for an `mk_` key), exactly as rosters (ADR-008) and
preferences (ADR-011) are keyed. A `category` label — a closed vocabulary,
`address | contact | identifier | credential-hint | convention | other` —
rides alongside the encrypted content: the category is a label, the content
is the ciphertext. `provenance` is the fingerprint hash of the capturing
turn, a digest, never content.

### Capture

Two paths, both classification-only on Jev and both fire-and-forget on the
gateway's existing capture path (a sibling of ADR-011's `maybeCapture`), so
capture never delays or fails a response:

- **Explicit:** "remember that …", "my <thing> is …". A Jev noul detects the
  intent to have Milo remember a durable personal fact.
- **Opportunistic:** a durable personal fact stated in passing. The same
  noul, leaning conservative, plus a Jev choice for the category.

The fact **text is extracted from the user's own message**, not generated by
Jev — Jev only classifies (should this be remembered, and as what category).
`resolveFactCapture(answers, message)` is pure and returns `{ category, text }`
or `undefined` below a confidence floor. The text is encrypted before it
lands in a row; it is the one value in Milo that is persisted from raw
content, by design, encrypted.

### Relevance-gated injection

Before a routed request is forwarded, one Jev call — given the request and the
caller's decrypted facts — classifies which facts, if any, are relevant to
*this* request (a noul per fact). Only relevant facts are appended, as a
single system note alongside the ADR-011 brief; `x-milo-facts-injected: <n>`
discloses how many. If none are relevant, nothing is injected and no fact
reaches the model. Injection is skipped on `low` posture, like the brief and
the gates.

This gate is both the **privacy** control (an irrelevant fact never leaves the
vault) and the **cost** control (input tokens grow only on the requests a
fact actually helps). The floor of the cost is one Jev relevance call per
routed request when the caller has any facts stored and injection is on;
facts add prompt tokens only when relevant.

## Consequences

Milo now persists user content, so it now has a real PII surface: the
encryption key becomes load-bearing (lose it and the facts are unreadable;
leak it and the ciphertext is readable), and the honest compliance note in
`docs/memory.md` says so. In exchange, an agent stops re-teaching Milo its
own operator's address and account ids every session, and the facts follow
the key across any client. `packages/core/src/types.ts` gains one optional
request field (`milo.facts`), which this ADR licenses.
